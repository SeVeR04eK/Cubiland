# Cubiland — Phase 2: Requirements Engineering

This package contains the initial draft requirements documents .

**Author:** Andrii Severyn · **Last updated:** 2026-11-11

## How These Documents Relate

The product-discovery set (`../product-discovery/`) defines *why* we're building this and *what we believe is true*. These requirements documents define *what the system must do*. When the two disagree, the discovery documents win until a product decision says otherwise — that's how a hypothesis stays a hypothesis instead of quietly becoming a spec.

Decisions already made are dated in the relevant document. Everything still marked `TBD` is a real open question, not a placeholder for an answer we already know.

## Documents

1. `PRD.md` — product vision, goals, scope, audience, and success metrics.
2. `USER_FLOWS.md` — high-level user journeys and alternative paths.
3. `USER_STORIES.md` — user needs expressed as testable stories.
4. `FUNCTIONAL_REQUIREMENTS.md` — observable system capabilities.
5. `NON_FUNCTIONAL_REQUIREMENTS.md` — quality attributes and operational constraints.
6. `BUSINESS_RULES.md` — product rules for learning, progression, rewards, shop, and Premium.
7. `ACCEPTANCE_CRITERIA.md` — conditions for accepting key capabilities.
8. `PRODUCT_ROADMAP.md` — proposed capability sequencing and dependencies.

## Review Notes

- All documents are initial drafts, not approved specifications.
- Unconfirmed product decisions are marked `TBD`.
- Priorities and phase assignments are provisional unless explicitly confirmed.
- Review the documents together: business rules, functional requirements, and acceptance criteria are intended to remain consistent.
- Product documentation is written in English.

## Suggested Review Order

`PRD.md` → `USER_FLOWS.md` → `USER_STORIES.md` → `FUNCTIONAL_REQUIREMENTS.md` → `BUSINESS_RULES.md` → `ACCEPTANCE_CRITERIA.md` → `NON_FUNCTIONAL_REQUIREMENTS.md` → `PRODUCT_ROADMAP.md`
